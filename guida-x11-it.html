01

Prima di iniziare

Non esiste un elenco universale delle applicazioni che “richiedono X11 forwarding”. La necessità dipende da dove gira il programma, dal backend e dalla modalità scelta. Una GUI X11 eseguita via SSH, da visualizzare sul computer locale usando il tunnel X11, necessita del forwarding; un comando testuale no.

01 / INDIZIO

Applicazione installata

Launcher, pacchetti e librerie aiutano a trovare candidati. Non provano il backend attivo.

02 / OSSERVAZIONE

Finestra X11

Una finestra identificata da xprop dimostra l’uso di X11 in quella sessione e modalità.

03 / VERIFICA

Avvio remoto riuscito

La prova attraverso SSH conferma che la specifica GUI funziona con quel tunnel e quella configurazione.

Serve nel tuo scenario?

Questa valutazione usa le tue risposte: non analizza il computer.

02

Preparare l’ambiente

I comandi seguenti sono per Bash su Ubuntu. Il computer locale è quello davanti a te; l’host remoto esegue il programma. Apri un terminale nell’ambiente indicato sopra ogni comando.

HOST UBUNTU DA ANALIZZARE · Bash
cat /etc/os-release
printf 'session=%s\nDISPLAY=%s\nWAYLAND_DISPLAY=%s\n' \
  "$XDG_SESSION_TYPE" "$DISPLAY" "$WAYLAND_DISPLAY"

Controlla VERSION_ID="22.04" e il nome della release; il sistema aggiornato può riportare un diverso livello di manutenzione. Nel desktop, x11 o wayland descrive la sessione, non ogni programma. In SSH il tipo di sessione può essere vuoto o tty.

Strumenti di indagine

Questa installazione modifica i pacchetti del sistema e richiede privilegi amministrativi e accesso ai repository. Installa x11-utils anche sul desktop che vuoi osservare, se diverso dall’host remoto.

HOST UBUNTU DA ANALIZZARE · Bash
sudo apt update
sudo apt install x11-utils x11-apps xauth

Lato locale

Servono un client SSH con supporto X11 e un server X funzionante. Su Ubuntu desktop può essere Xorg oppure Xwayland in una sessione Wayland. Su Windows o macOS occorre predisporre un server X compatibile e configurare il client SSH scelto; i comandi Bash qui non configurano quei sistemi.

Lato remoto

Servono l’applicazione, le sue dipendenze, xauth e un server OpenSSH configurato. Non è necessario installare un intero desktop o avviare Xorg remoto solo per il forwarding. Se SSH non è presente, l’installazione di openssh-server abilita un servizio di accesso remoto e va pianificata separatamente.

Riferimenti: ssh(1) · Ubuntu Jammy · Xwayland · Wayland documentation

03

Cercare le applicazioni

Obiettivo: trovare software già presente. Le ricerche dei launcher e dei pacchetti non installano software, non richiedono sudo e non avviano le applicazioni. Per ldd valgono le precauzioni riportate sotto. Esegui le ricerche sul computer Ubuntu che dovrà eseguire la GUI, prima di installare gli strumenti diagnostici se vuoi fotografare lo stato iniziale.

I tre comandi rapidi: uso e interpretazione

Eccoli nella forma originale, da eseguire in Bash sull’host Ubuntu da analizzare. Sono strumenti di prima indagine: i risultati vanno interpretati prima di provare il forwarding. Più sotto trovi varianti e un inventario strutturato.

1. Estrarre i nomi dai launcher desktop

HOST UBUNTU DA ANALIZZARE · Bash
grep -r "Name=" /usr/share/applications/*.desktop | cut -d'=' -f2-

Come funziona: Bash espande *.desktop nei file presenti direttamente in /usr/share/applications. grep cerca le righe contenenti Name=; cut usa = come separatore e mantiene tutto dal secondo campo in poi. Il risultato è una lista di valori, non di comandi eseguibili.

Limiti: il filtro può includere GenericName= e i nomi delle azioni secondarie; non seleziona Name[it]=. Perde l’associazione al file e può generare duplicati. Con questo glob, -r non rende la ricerca un inventario completo delle sottocartelle. Mancano i launcher utente e quelli Snap/Flatpak in altri percorsi. Un nome restituito non garantisce una GUI X11; nessun risultato non dimostra che non siano installate GUI.

Variante più selettiva per la chiave Name, ancora limitata a questa cartella e senza distinguere i gruppi Desktop Entry/Action:

HOST UBUNTU DA ANALIZZARE · Bash
grep -h '^Name=' /usr/share/applications/*.desktop | cut -d'=' -f2- | sort -u

Desktop Entry Specification · Name, Type, Exec, Terminal

Dal nome al percorso e al comando di avvio

Nel tuo esempio, “New Window”, “New Session” e “Preferences” possono essere azioni di un launcher; “Process Viewer” e “Text Editor” possono essere descrizioni GenericName. Il solo elenco non permette di associare queste righe a un file preciso. La ricerca seguente legge soltanto il gruppo Desktop Entry e conserva il percorso completo.

inventory-launchers.py · Python 3
"""Inspect desktop launchers without running applications or shell commands."""

from __future__ import annotations

import argparse
import configparser
import os
from pathlib import Path
import re
import shlex
import shutil
import sys


def launcher_directories() -> list[Path]:
    """Return common and configured XDG application directories."""
    home = Path.home()
    data_home = os.environ.get("XDG_DATA_HOME") or str(home / ".local/share")
    data_dirs = os.environ.get("XDG_DATA_DIRS") or "/usr/local/share:/usr/share"
    roots = [Path(data_home), *(Path(p) for p in data_dirs.split(":") if p)]
    roots += [Path("/var/lib/snapd/desktop"), Path("/var/lib/flatpak/exports/share"),
              home / ".local/share/flatpak/exports/share"]
    return list(dict.fromkeys(root / "applications" for root in roots if root.is_absolute()))


def read_entry(path: Path) -> dict[str, str]:
    """Read only the main Desktop Entry group, preserving raw Exec syntax."""
    parser = configparser.ConfigParser(interpolation=None, delimiters=("=",), strict=True)
    parser.optionxform = str
    with path.open(encoding="utf-8-sig") as source:
        parser.read_file(source)
    return dict(parser.items("Desktop Entry")) if parser.has_section("Desktop Entry") else {}


def executable_path(exec_value: str) -> str:
    """Resolve a simple first executable; leave complex Exec quoting unresolved."""
    match = re.match(r'''^(?:"([^"\\%`$]+)"|([^\s"'\\%`$><|&;()=]+))(?=\s|$)''', exec_value.strip())
    if not match:
        return ""
    first = match.group(1) or match.group(2)
    if "/" in first and not os.path.isabs(first):
        return ""
    located = shutil.which(first)
    return os.path.abspath(located) if located else ""


def printable(value: str) -> str:
    """Escape control characters so metadata cannot manipulate terminal output."""
    return "".join(c if c.isprintable() else f"\\x{ord(c):02x}" for c in value)


def describe(path: Path, entry: dict[str, str], italian: bool) -> str:
    """Format paths, raw Exec and an explicit launcher command as a readable card."""
    def text(it: str, en: str) -> str:
        return it if italian else en

    path = path.absolute()
    raw = entry.get("Exec", "")
    executable = executable_path(raw)
    gio = shutil.which("gio")
    launch = shlex.join([os.path.abspath(gio), "launch", str(path)]) if gio else text(
        "gio non trovato: richiede libglib2.0-bin", "gio not found: requires libglib2.0-bin")
    fields = [
        ("NAME", entry.get("Name", path.stem)),
        ("DESKTOP FILE", str(path)),
        ("EXEC (RAW)", raw or text("assente: controllare D-Bus", "absent: check D-Bus")),
        ("EXECUTABLE", executable or text("non risolto: assente o sintassi complessa", "unresolved: missing or complex syntax")),
        ("TRYEXEC", entry.get("TryExec", "—")),
        ("TERMINAL", entry.get("Terminal", "false")),
        ("DBUS ACTIVATABLE", entry.get("DBusActivatable", "false")),
        ("NO DISPLAY", entry.get("NoDisplay", "false")),
        ("WORKING DIR", entry.get("Path", "—")),
        ("LAUNCH", launch),
    ]
    return "\n".join(f"{label:18} {printable(value)}" for label, value in fields)


def main() -> None:
    """Print candidate launchers; --match filters name, command and desktop path."""
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("--lang", choices=("it", "en"), default="it")
    parser.add_argument("--match", default="")
    parser.add_argument("--directory", type=Path, action="append", help="Scan only these directories")
    args = parser.parse_args()
    candidates: set[Path] = set()
    for root in args.directory or launcher_directories():
        if root.is_dir():
            candidates.update(p.absolute() for p in root.rglob("*.desktop") if p.is_file())
    found = 0
    for path in sorted(candidates):
        try:
            entry = read_entry(path)
        except (OSError, UnicodeError, configparser.Error) as error:
            print(f"SKIP {printable(str(path))}: {printable(str(error))}", file=sys.stderr)
            continue
        if entry.get("Type") != "Application" or entry.get("Hidden") == "true":
            continue
        haystack = " ".join([entry.get("Name", ""), entry.get("Exec", ""), str(path)])
        if args.match.casefold() not in haystack.casefold():
            continue
        found += 1
        print(f"\n[{found:03}] " + "─" * 55)
        print(describe(path, entry, args.lang == "it"))
    print(f"\nTOTAL: {found}")


if __name__ == "__main__":
    main()

Le due righe sono alternative: tutte le voci, oppure solo quelle corrispondenti a tilix. Per BleachBit, Stacer o TigerVNC modifica --match. Esegui come l’utente che utilizzerà le applicazioni: root ha HOME, PATH e launcher personali differenti.

CampoCosa significa
DESKTOP FILEPercorso assoluto del launcher effettivamente letto.
EXEC (RAW)Voce Exec originale, inclusi argomenti e segnaposto. Non incollarla automaticamente nella shell.
EXECUTABLEPercorso del primo eseguibile risolto nel PATH corrente, se la sintassi è semplice. Può essere env, pkexec, snap o un wrapper, non il programma finale. Non vengono dereferenziati i link simbolici.
LAUNCHComando completo per chiedere a gio di lanciare quel file desktop, conservandone la semantica. È stampato, non eseguito. Non garantisce l’avvio o il forwarding.
TERMINAL / DBUS ACTIVATABLEEvidenziano avvio in terminale e possibile attivazione D-Bus. Le voci Terminal=true sono mantenute per riconoscere Htop/Vim senza confonderli con GUI X11.

Avvio via SSH: dopo aver verificato xclock, copia soltanto la riga LAUNCH del programma fidato scelto nella stessa sessione. gio interpreta il launcher; D-Bus, istanze esistenti, autorizzazioni e terminali mancanti possono ancora impedirne l’avvio o riutilizzare un’altra sessione. Per la variante “as root”, controlla Exec: l’elevazione dei privilegi non è necessaria per il normale test X11.

Limiti dichiarati: inventario per file, non ricostruzione del menu. Conserva NoDisplay, non risolve le precedenze utente/sistema e non prova TryExec. Il parser mantiene il nome base; riporta Exec senza decodificare gli escape. Sintassi complesse o binari assenti restano “non risolti”, senza inventare percorsi. Il rapporto a schede non è TSV: non incollarlo nell’importatore TSV più sotto.

Se gio manca, il pacchetto Ubuntu è libglib2.0-bin. L’eventuale installazione con sudo apt install libglib2.0-bin modifica il sistema; non serve per raccogliere i metadati.

2. Cercare le dipendenze X11 di gedit

Usa ldd soltanto su un eseguibile fidato. Questo esempio presuppone che gedit e which siano disponibili e che il percorso trovato sia un eseguibile dinamico, non un wrapper. ldd può provocare esecuzione di codice: non usarlo su file sconosciuti.
HOST UBUNTU DA ANALIZZARE · Bash
ldd $(which gedit) | grep -i "libX11\|libxcb"

Come funziona: $(which gedit) viene sostituito con il percorso di gedit; ldd elenca le dipendenze dinamiche risolte. grep -i ignora maiuscole/minuscole e, con GNU grep di Ubuntu, \| significa “oppure”: vengono mantenute le righe con libX11 o libxcb.

Come leggere il risultato: una riga come libX11.so.6 => … è un indizio di collegamento, anche indiretto. not found indica invece una dipendenza non risolta. Nessun risultato può dipendere da plugin, wrapper, assenza del programma o errori: non prova l’incompatibilità con X11. Neppure una corrispondenza prova il backend attivo o il successo via SSH.

Variante con controllo di presenza, percorso tra virgolette e alternanza esplicita grep -E. Verifica comunque prima il tipo e la provenienza del file; sostituisci gedit con l’applicazione candidata.

HOST UBUNTU DA ANALIZZARE · Bash
app_path=$(command -v gedit)
if [ -n "$app_path" ]; then
  ldd "$app_path" | grep -Ei 'libX11|libxcb'
else
  printf '%s\n' 'gedit: command not found in PATH' >&2
fi

3. Cercare componenti GTK, Qt e X server nei pacchetti

HOST UBUNTU DA ANALIZZARE · Bash
dpkg -l | grep -E "libgtk|libqt|xserver"

Come funziona: dpkg elenca i record dei pacchetti; grep -E mantiene le righe contenenti libgtk, libqt oppure xserver. Il confronto è sensibile a maiuscole/minuscole e riguarda l’intera riga, comprese le descrizioni.

Come leggere il risultato: nella colonna iniziale, ii indica normalmente un pacchetto installato; rc un pacchetto rimosso con configurazioni residue. Il comando originale non filtra gli stati. Mostra soprattutto componenti grafici, non l’elenco completo delle applicazioni che ne dipendono, e non copre Snap/Flatpak. Nessun risultato non esclude applicazioni X11.

Variante limitata alle righe con stato ii; per ricercare le applicazioni tramite le loro dipendenze usa invece il filtro sul campo Depends riportato più sotto.

HOST UBUNTU DA ANALIZZARE · Bash
dpkg -l | awk '$1 == "ii"' | grep -E "libgtk|libqt|xserver"

Una tabella leggibile dei pacchetti installati

HOST UBUNTU DA ANALIZZARE · Bash
{
  printf 'PACKAGE\tVERSION\tARCH\tDESCRIPTION\n'
  dpkg-query -W -f='${db:Status-Status}\t${binary:Package}\t${Version}\t${Architecture}\t${binary:Summary}\n' |
    awk -F '\t' '$1 == "installed" && $2 ~ /(libgtk|libqt|xserver)/ {
      print $2 "\t" $3 "\t" $4 "\t" $5

} | column -t -s "$(printf '\t')"

Le intestazioni distinguono pacchetto, versione, architettura e descrizione breve. Vengono selezionati solo pacchetti con stato installed; la ricerca riguarda il nome del pacchetto, non la descrizione. column allinea le tabulazioni senza tagliare versioni o nomi. Per questo i risultati possono differire dal grep sull’intera riga originale.

Se column non è presente, rimuovi | column … per ottenere TSV; il pacchetto Ubuntu che fornisce column è bsdextrautils. Su un terminale stretto usa il rapporto a schede seguente, che evita una tabella molto larga.

HOST UBUNTU DA ANALIZZARE · Bash

Inventario strutturato dei candidati desktop

Il comando seguente produce righe separate da tabulazioni (TSV): legge solo il gruppo principale Desktop Entry ed esclude Type diverso da Application, Hidden=true e Terminal=true. Non esegue Exec o TryExec.

HOST UBUNTU DA ANALIZZARE · Bash
printf 'Name\tExec\tTerminal\tTryExec\tDesktopFile\n'
for dir in /usr/share/applications /usr/local/share/applications \
  "${XDG_DATA_HOME:-$HOME/.local/share}/applications" \
  /var/lib/snapd/desktop/applications \
  /var/lib/flatpak/exports/share/applications \
  "$HOME/.local/share/flatpak/exports/share/applications"; do
  [ -d "$dir" ] || continue
  find -L "$dir" -type f -name '*.desktop' -exec awk '
    /^\[Desktop Entry\]\r?$/ { main=1; next }
    /^\[/ { main=0 }
    main && /^[A-Za-z]+=/ {
      key=$0; sub(/=.*/, "", key)
      value=$0; sub(/^[^=]*=/, "", value); sub(/\r$/, "", value)
      gsub(/\t/, " ", value); field[key]=value
    }
    END {
      if (field["Type"] == "Application" && field["Hidden"] != "true" &&
          field["Terminal"] != "true") {
        printf "%s\t%s\t%s\t%s\t%s\n", field["Name"], field["Exec"],
          field["Terminal"], field["TryExec"], FILENAME
      }
    }' {} \;
done

Conserva anche NoDisplay e i launcher senza Exec per non perdere candidati attivabili tramite D-Bus. Name è il nome base, non la traduzione del desktop. Il filtro non prova che esista una finestra o che il programma sia installato correttamente.

Limiti: inventario per file, non ricostruzione del menu. Può contenere duplicati o launcher obsoleti; non risolve la precedenza tra copie utente/sistema, OnlyShowIn/NotShowIn o tutti i percorsi XDG_DATA_DIRS personalizzati. L’esclusione di Terminal=true può omettere programmi con modalità miste.

Pacchetti installati con dipendenze grafiche

HOST UBUNTU DA ANALIZZARE · Bash
dpkg-query -W -f='${db:Status-Status}\t${binary:Package}\t${Version}\t${Depends}\n' |
  awk -F '\t' '$1 == "installed" &&
    $4 ~ /(^|[ ,|])(libx11-6|libxcb1|libgtk-3-0|libgtk2.0-0|libgtk-4-1|libqt5gui5|libqt5widgets5|libqt6gui6|libqt6widgets6)([ :,(|]|$)/ {
      print $2 "\t" $3 "\t" $4
    }'

Qui cerchi nel campo Depends dei pacchetti realmente installati, non soltanto nel nome del pacchetto. Possono comparire librerie o componenti senza interfaccia: controlla i candidati. Il filtro è parziale (dipendenze dirette dichiarate); può perdere dipendenze transitive, plugin e altri toolkit. Non copre il contenuto di Snap, Flatpak o AppImage.

dpkg-query(1) · Ubuntu Jammy

Perché i tre comandi proposti non danno una certezza
  • grep -r "Name=" … può includere GenericName e nomi delle azioni, oltre a perdere launcher in altri percorsi. Un .desktop può avviare un servizio o un programma testuale.
  • ldd … | grep libX11 mostra un collegamento a librerie: non prova il backend scelto, né il funzionamento remoto. GTK e Qt supportano più backend e non sono semplicemente “librerie di Xorg”.
  • dpkg -l | grep -E "libgtk|libqt|xserver" filtra righe per testo: trova soprattutto librerie/server, non tutte le applicazioni che li usano; può includere stati diversi da installato. Il server X remoto non è un requisito del forwarding.

Conclusione: individua il candidato → verifica il comando/pacchetto → osserva X11 → prova la GUI via SSH. Nessuno dei filtri è una “certezza matematica”.

Approfondimento: tutti i metadati dei launcher

Esegui come l’utente interessato. Il comando cerca nei percorsi comuni dei launcher, comprese le esportazioni Snap e Flatpak; ignora le cartelle assenti.

HOST UBUNTU DA ANALIZZARE · Bash
for dir in /usr/share/applications /usr/local/share/applications \
  "$HOME/.local/share/applications" /var/lib/snapd/desktop/applications \
  /var/lib/flatpak/exports/share/applications \
  "$HOME/.local/share/flatpak/exports/share/applications"; do
  [ -d "$dir" ] || continue
  grep -RHnE '^(Name|Exec|TryExec|Terminal|Type|Hidden|NoDisplay)=' \
    "$dir" --include='*.desktop'
done

Exec= indica il comando di avvio; Terminal=false significa che non viene richiesto un terminale, non che l’app usi X11. Campi come %U e %F sono segnaposto del launcher: non incollarli alla cieca in Bash. Possono comparire azioni secondarie, duplicati e launcher nascosti; percorsi XDG personalizzati e software senza launcher possono sfuggire.

Riferimenti: Desktop Entry Specification · freedesktop.org

Completa l’inventario: APT, Snap e Flatpak

HOST UBUNTU DA ANALIZZARE · Bash
dpkg-query -W -f='${binary:Package}\t${db:Status-Status}\t${Version}\n' | \
  awk -F '\t' '$2 == "installed" {print $1 "\t" $3}'
if command -v snap >/dev/null 2>&1; then snap list; fi
if command -v flatpak >/dev/null 2>&1; then flatpak list --app; fi

L’elenco include anche software senza GUI. Un pacchetto APT non copre automaticamente Snap, Flatpak, AppImage, programmi in /opt o installazioni manuali. Per ogni candidato annota nome, versione, origine e comando. Non avviare in massa gli Exec trovati.

Approfondimento: cercare indizi nelle librerie

Opzionale: installa binutils e file per questi comandi. L’esempio usa xclock; sostituiscilo con l’eseguibile che hai individuato.

HOST UBUNTU DA ANALIZZARE · Bash
app_path=$(command -v xclock)
if [ -n "$app_path" ]; then
  file -L "$app_path"
  readelf -d "$app_path" | grep NEEDED
fi

libX11, libxcb, GTK o Qt sono indizi, non una sentenza. readelf mostra dipendenze ELF dirette, non tutte quelle transitive o caricate come plugin. Script, wrapper e binari statici richiedono un’analisi diversa; un errore “not an ELF file” non esclude una GUI. Evita ldd su eseguibili non fidati.

Riferimenti: readelf(1) · Ubuntu Jammy

Usare ldd solo su un eseguibile fidato

Dopo aver verificato con file che il percorso sia un ELF dinamico fidato, puoi ispezionare anche le dipendenze risolte da ldd. L’esempio usa xclock; non usare un wrapper o un file sconosciuto.

HOST UBUNTU DA ANALIZZARE · Bash
app_path=$(command -v xclock)
if [ -n "$app_path" ]; then
  ldd "$app_path" | grep -Ei 'libX11|libxcb'
fi

Un risultato segnala librerie collegate, anche indirettamente; nessun risultato non esclude plugin caricati a runtime. Non è una prova di necessità o compatibilità del forwarding. Per eseguibili non fidati preferisci l’ispezione statica con readelf: ldd può provocare esecuzione di codice.

Riferimenti: ldd(1) · Ubuntu Jammy

04

Osservare X11

Per esaminare le applicazioni già aperte, usa un terminale dentro il desktop interessato, come il suo utente. Una sessione SSH con forwarding può puntare al display locale del client, non al desktop fisico remoto.

TERMINALE DEL DESKTOP DA ANALIZZARE · Bash
printf 'DISPLAY=%s\n' "$DISPLAY"
xlsclients -l
xprop WM_CLASS WM_NAME _NET_WM_PID WM_CLIENT_MACHINE

Con xprop il puntatore cambia: fai clic sulla finestra da identificare. WM_CLASS aiuta a riconoscere l’app; _NET_WM_PID, se presente e corretto, indica un processo sul computer dichiarato da WM_CLIENT_MACHINE. Non usare quel PID sul computer sbagliato.

Limite importante. xlsclients non è un censimento completo: dipende dalle proprietà pubblicate dai client. Non mostra le finestre Wayland native e può omettere client X11. Su Wayland, una finestra riconosciuta da xprop usa X11 tramite Xwayland. L’assenza dall’elenco non prova che un’app sia Wayland.

Riferimenti: xlsclients(1) · Ubuntu Jammy · xprop(1) · Ubuntu Jammy · Xwayland · Wayland documentation

Dal PID al processo e al suo ambiente

Sul computer che esegue il processo, sostituisci 1234 con il PID verificato. Usa i tuoi processi: permessi, container e namespace possono limitare la visibilità.

HOST UBUNTU DA ANALIZZARE · Bash
target_pid=1234
ps -p "$target_pid" -o pid=,user=,comm=,args=
readlink -f "/proc/$target_pid/exe"
tr '\0' '\n' < "/proc/$target_pid/environ" | \
  grep -E '^(DISPLAY|WAYLAND_DISPLAY|GDK_BACKEND|QT_QPA_PLATFORM)='

DISPLAY o WAYLAND_DISPLAY nell’ambiente sono solo indizi ereditati: non dimostrano una connessione né il backend effettivamente usato. Il PID può essere terminato, riutilizzato o non pubblicato dalla finestra.

05

Verificare via SSH

1. Verifica il servizio remoto

HOST UBUNTU DA ANALIZZARE · Bash
command -v xauth
sudo /usr/sbin/sshd -T | grep -E '^(x11forwarding|x11uselocalhost|disableforwarding|xauthlocation) '

Controlla x11forwarding yes, x11uselocalhost yes e disableforwarding no. Con regole Match, usa anche sshd -T -C con utente e indirizzi reali: la configurazione globale potrebbe non essere quella della connessione. Le restrizioni della chiave SSH possono vietare il forwarding.

Se la configurazione deve essere corretta

L’amministratore deve verificare /etc/ssh/sshd_config, i file inclusi e le regole Match. Impostare X11Forwarding yes mantenendo X11UseLocalhost yes dove appropriato; non aggiungere direttive duplicate alla cieca. Dopo la modifica, valida e ricarica il servizio:

HOST UBUNTU DA ANALIZZARE · Bash
sudo /usr/sbin/sshd -t && sudo systemctl reload ssh

Mantieni aperta la sessione corrente e prova una nuova connessione. La ricarica non aggiunge il forwarding a una sessione già aperta.

Riferimenti: sshd_config(5) · Ubuntu Jammy

2. Apri il tunnel dal computer locale

Da un terminale Ubuntu locale con server X disponibile. Sostituisci utente@host con la tua destinazione. Prima verifica che DISPLAY sia valorizzato sul client.

CLIENT SSH · COMPUTER LOCALE · Bash
printf 'DISPLAY=%s\n' "$DISPLAY"
ssh -X -o ForwardX11Trusted=no utente@host

Questo comando richiede esplicitamente forwarding non trusted. Su Ubuntu/Debian -X da solo può essere già trusted; non dedurre il livello di fiducia dalla sola lettera. Un’app incompatibile con le restrizioni può richiedere ssh -Y, da usare solo con host e applicazioni fidati: consente ampio accesso al display locale.

3. Prova una finestra semplice

NUOVA SESSIONE SSH · HOST REMOTO · Bash
printf 'DISPLAY=%s\n' "$DISPLAY"
xclock

Un valore come localhost:10.0 è tipico, non obbligatorio. Se l’orologio appare sul tuo schermo, il percorso X11 funziona per quel client. Chiudilo per tornare al prompt. Non impostare manualmente DISPLAY a :0 o all’IP del computer: aggireresti il display predisposto da SSH.

Riferimenti: ssh(1) · Ubuntu Jammy

4. Prova l’applicazione candidata

Nella stessa sessione, avvia una singola applicazione fidata con il comando identificato prima. Per evitare di riutilizzare un processo già aperto, chiudi prima le sue istanze dopo aver salvato il lavoro oppure usa l’opzione di nuova istanza documentata dal programma.

SESSIONE SSH · ESEMPI DA ADATTARE · Bash
GDK_BACKEND=x11 nome_app_gtk
QT_QPA_PLATFORM=xcb nome_app_qt

Le due righe sono alternative per GTK 3 e Qt 5: sostituisci il nome con un comando reale ed esegui solo quella pertinente. Funzionano se la build include il backend e le dipendenze necessarie. Non cambiano globalmente il desktop. D-Bus, sandbox, accelerazione grafica o istanze già aperte possono complicare l’avvio.

Riferimenti: GTK 3 · Running applications · Qt 5 · QGuiApplication

06

Risolvere gli errori

DISPLAY vuoto o “Can’t open display”
Controlla prima il server X e DISPLAY sul computer locale, poi connettiti nuovamente con forwarding. Verifica xauth e la configurazione effettiva di sshd. Per i dettagli usa ssh -vv -X -o ForwardX11Trusted=no utente@host. I log possono contenere nomi e indirizzi: oscurali prima di condividerli.
“Authorization required” o cookie X11 rifiutato
Prova come utente della sessione SSH, senza sudo per avviare la GUI. Verifica proprietario e permessi del file di autorizzazione (XAUTHORITY, se impostato) e riconnettiti. Non pubblicare i cookie xauth e non usare xhost + come scorciatoia.
Il desktop è Wayland e xlsclients mostra poco
È atteso per le app Wayland native. xlsclients osserva il display X selezionato; non il compositor Wayland. Prova xprop sulla finestra e verifica il backend documentato dall’applicazione.
“Could not load the Qt platform plugin xcb”
Controlla le dipendenze del plugin e l’ambiente Qt della specifica installazione. Il messaggio non dimostra da solo un errore del tunnel. Conferma prima xclock e non mescolare librerie Qt di installazioni differenti.
Funziona all’inizio, poi i nuovi avvii falliscono
In modalità non trusted, ForwardX11Timeout limita nel tempo l’accettazione di nuove connessioni X11 (predefinito upstream: 20 minuti). Riapri una sessione e controlla la configurazione client. Verifica inoltre disconnessioni SSH e sospensione del computer.
Snap, Flatpak, browser o GUI lenta
Verifica i permessi grafici e le limitazioni del pacchetto specifico, oltre a D-Bus e accelerazione. Non disabilitare la sandbox come rimedio generico. X11 forwarding non garantisce GPU remota, audio o buone prestazioni su reti ad alta latenza; un desktop remoto può essere più adatto.
