01

Before you start

There is no universal list of applications that “require X11 forwarding”. The need depends on where a program runs, its backend and the selected mode. An X11 GUI launched over SSH and displayed on your local computer using the X11 tunnel needs forwarding; a text command does not.

01 / CLUE

Installed application

Launchers, packages and libraries help find candidates. They do not prove the active backend.

02 / OBSERVATION

X11 window

A window identified by xprop demonstrates X11 usage in that session and mode.

03 / VERIFICATION

Successful remote launch

A test through SSH confirms that the particular GUI works with that tunnel and configuration.

Does your scenario need it?

This assessment uses your answers; it does not scan your computer.

02

Prepare the environment

The commands below target Bash on Ubuntu. The local computer is the one in front of you; the remote host runs the program. Open a terminal in the environment shown above each command.

UBUNTU HOST TO INSPECT · Bash
cat /etc/os-release
printf 'session=%s\nDISPLAY=%s\nWAYLAND_DISPLAY=%s\n' \
  "$XDG_SESSION_TYPE" "$DISPLAY" "$WAYLAND_DISPLAY"

Check VERSION_ID="22.04" and the release name; an updated system may report a different maintenance level. On the desktop, x11 or wayland describes the session, not every program. In SSH, the session type may be empty or tty.

Investigation tools

This installation changes system packages and requires administrator privileges and repository access. Install x11-utils on the desktop you want to inspect too, if it differs from the remote host.

UBUNTU HOST TO INSPECT · Bash
sudo apt update
sudo apt install x11-utils x11-apps xauth

Local side

You need an SSH client with X11 support and a working X server. On an Ubuntu desktop this can be Xorg or Xwayland in a Wayland session. Windows and macOS need a compatible X server and the chosen SSH client configured; the Bash commands here do not configure those systems.

Remote side

You need the application, its dependencies, xauth and a configured OpenSSH server. A complete desktop or a running remote Xorg server is not required solely for forwarding. If SSH is absent, installing openssh-server enables a remote-access service and should be planned separately.

References: ssh(1) · Ubuntu Jammy · Xwayland · Wayland documentation

03

Find applications

Goal: find software already present. Launcher and package searches do not install software, require sudo or launch applications. For ldd, follow the precautions below. Run the searches on the Ubuntu computer that will run the GUI, before installing diagnostic tools if you want a snapshot of the initial state.

The three quick commands: usage and interpretation

Here they are in their original form, to run in Bash on the Ubuntu host you want to inspect. They are initial investigation tools: interpret their results before testing forwarding. Variants and a structured inventory follow below.

1. Extract names from desktop launchers

UBUNTU HOST TO INSPECT · Bash
grep -r "Name=" /usr/share/applications/*.desktop | cut -d'=' -f2-

How it works: Bash expands *.desktop to files directly inside /usr/share/applications. grep selects lines containing Name=; cut uses = as the delimiter and keeps everything from the second field onward. The result is a list of values, not executable commands.

Limitations: the filter may include GenericName= and secondary action names; it does not select Name[it]=. It loses the file association and can produce duplicates. With this glob, -r does not make the search a complete subdirectory inventory. User launchers and Snap/Flatpak launchers in other locations are missed. A returned name does not guarantee an X11 GUI; no output does not prove that no GUIs are installed.

A more selective variant for the Name key, still restricted to this directory and unable to distinguish Desktop Entry/Action groups:

UBUNTU HOST TO INSPECT · Bash
grep -h '^Name=' /usr/share/applications/*.desktop | cut -d'=' -f2- | sort -u

Desktop Entry Specification · Name, Type, Exec, Terminal

From the name to the path and launch command

In your example, “New Window”, “New Session” and “Preferences” may be launcher actions; “Process Viewer” and “Text Editor” may be GenericName descriptions. The list alone cannot associate these lines with an exact file. The following search reads only the Desktop Entry group and retains the full path.

Copy the complete script into a Python file

Create a text file named inventory-launchers.py, press Copy on the block below and paste its contents into your editor. Save as UTF-8, preserving indentation and the .py extension (not .py.txt). The block contains only Python, with no Bash commands or PY delimiters. The full script is included in the offline guide too.

inventory-launchers.py · Python 3
"""Inspect desktop launchers without running applications or shell commands."""

from __future__ import annotations

import argparse
import configparser
import os
from pathlib import Path
import re
import shlex
import shutil
import sys


def launcher_directories() -> list[Path]:
    """Return common and configured XDG application directories."""
    home = Path.home()
    data_home = os.environ.get("XDG_DATA_HOME") or str(home / ".local/share")
    data_dirs = os.environ.get("XDG_DATA_DIRS") or "/usr/local/share:/usr/share"
    roots = [Path(data_home), *(Path(p) for p in data_dirs.split(":") if p)]
    roots += [Path("/var/lib/snapd/desktop"), Path("/var/lib/flatpak/exports/share"),
              home / ".local/share/flatpak/exports/share"]
    return list(dict.fromkeys(root / "applications" for root in roots if root.is_absolute()))


def read_entry(path: Path) -> dict[str, str]:
    """Read only the main Desktop Entry group, preserving raw Exec syntax."""
    parser = configparser.ConfigParser(interpolation=None, delimiters=("=",), strict=True)
    parser.optionxform = str
    with path.open(encoding="utf-8-sig") as source:
        parser.read_file(source)
    return dict(parser.items("Desktop Entry")) if parser.has_section("Desktop Entry") else {}


def executable_path(exec_value: str) -> str:
    """Resolve a simple first executable; leave complex Exec quoting unresolved."""
    match = re.match(r'''^(?:"([^"\\%`$]+)"|([^\s"'\\%`$><|&;()=]+))(?=\s|$)''', exec_value.strip())
    if not match:
        return ""
    first = match.group(1) or match.group(2)
    if "/" in first and not os.path.isabs(first):
        return ""
    located = shutil.which(first)
    return os.path.abspath(located) if located else ""


def printable(value: str) -> str:
    """Escape control characters so metadata cannot manipulate terminal output."""
    return "".join(c if c.isprintable() else f"\\x{ord(c):02x}" for c in value)


def describe(path: Path, entry: dict[str, str], italian: bool) -> str:
    """Format paths, raw Exec and an explicit launcher command as a readable card."""
    def text(it: str, en: str) -> str:
        return it if italian else en

    path = path.absolute()
    raw = entry.get("Exec", "")
    executable = executable_path(raw)
    gio = shutil.which("gio")
    launch = shlex.join([os.path.abspath(gio), "launch", str(path)]) if gio else text(
        "gio non trovato: richiede libglib2.0-bin", "gio not found: requires libglib2.0-bin")
    fields = [
        ("NAME", entry.get("Name", path.stem)),
        ("DESKTOP FILE", str(path)),
        ("EXEC (RAW)", raw or text("assente: controllare D-Bus", "absent: check D-Bus")),
        ("EXECUTABLE", executable or text("non risolto: assente o sintassi complessa", "unresolved: missing or complex syntax")),
        ("TRYEXEC", entry.get("TryExec", "—")),
        ("TERMINAL", entry.get("Terminal", "false")),
        ("DBUS ACTIVATABLE", entry.get("DBusActivatable", "false")),
        ("NO DISPLAY", entry.get("NoDisplay", "false")),
        ("WORKING DIR", entry.get("Path", "—")),
        ("LAUNCH", launch),
    ]
    return "\n".join(f"{label:18} {printable(value)}" for label, value in fields)


def main() -> None:
    """Print candidate launchers; --match filters name, command and desktop path."""
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("--lang", choices=("it", "en"), default="it")
    parser.add_argument("--match", default="")
    parser.add_argument("--directory", type=Path, action="append", help="Scan only these directories")
    args = parser.parse_args()
    candidates: set[Path] = set()
    for root in args.directory or launcher_directories():
        if root.is_dir():
            candidates.update(p.absolute() for p in root.rglob("*.desktop") if p.is_file())
    found = 0
    for path in sorted(candidates):
        try:
            entry = read_entry(path)
        except (OSError, UnicodeError, configparser.Error) as error:
            print(f"SKIP {printable(str(path))}: {printable(str(error))}", file=sys.stderr)
            continue
        if entry.get("Type") != "Application" or entry.get("Hidden") == "true":
            continue
        haystack = " ".join([entry.get("Name", ""), entry.get("Exec", ""), str(path)])
        if args.match.casefold() not in haystack.casefold():
            continue
        found += 1
        print(f"\n[{found:03}] " + "─" * 55)
        print(describe(path, entry, args.lang == "it"))
    print(f"\nTOTAL: {found}")


if __name__ == "__main__":
    main()

2. Look for gedit’s X11 dependencies

Use ldd only on a trusted executable. This example assumes that gedit and which are available and that the resolved path is a dynamic executable, not a wrapper. ldd can cause code execution: do not use it on unknown files.
UBUNTU HOST TO INSPECT · Bash
ldd $(which gedit) | grep -i "libX11\|libxcb"

How it works: $(which gedit) is replaced with the path to gedit; ldd lists resolved dynamic dependencies. grep -i ignores case and, with Ubuntu’s GNU grep, \| means “or”: lines containing libX11 or libxcb are retained.

Reading the result: a line such as libX11.so.6 => … is evidence of a dependency, possibly indirect. not found instead indicates an unresolved dependency. Empty output may be caused by plugins, wrappers, a missing program or errors: it does not prove X11 incompatibility. A match does not prove the active backend or successful operation over SSH either.

A variant with a presence check, a quoted path and explicit grep -E alternation. Still check the file type and origin first; replace gedit with the candidate application.

UBUNTU HOST TO INSPECT · Bash
app_path=$(command -v gedit)
if [ -n "$app_path" ]; then
  ldd "$app_path" | grep -Ei 'libX11|libxcb'
else
  printf '%s\n' 'gedit: command not found in PATH' >&2
fi

ldd(1) · Ubuntu Jammy

3. Find GTK, Qt and X server components in package records

UBUNTU HOST TO INSPECT · Bash
dpkg -l | grep -E "libgtk|libqt|xserver"

How it works: dpkg lists package records; grep -E retains lines containing libgtk, libqt or xserver. Matching is case-sensitive and applies to the entire line, including descriptions.

Reading the result: in the first column, ii normally indicates an installed package; rc a removed package with residual configuration files. The original command does not filter status. It mainly shows graphics components, not a complete list of applications depending on them, and does not cover Snap/Flatpak. No output does not rule out X11 applications.

A variant restricted to rows with ii status; to find applications through their dependencies, use the Depends-field filter further below instead.

UBUNTU HOST TO INSPECT · Bash
dpkg -l | awk '$1 == "ii"' | grep -E "libgtk|libqt|xserver"

A readable table of installed packages

UBUNTU HOST TO INSPECT · Bash
{
  printf 'PACKAGE\tVERSION\tARCH\tDESCRIPTION\n'
  dpkg-query -W -f='${db:Status-Status}\t${binary:Package}\t${Version}\t${Architecture}\t${binary:Summary}\n' |
    awk -F '\t' '$1 == "installed" && $2 ~ /(libgtk|libqt|xserver)/ {
      print $2 "\t" $3 "\t" $4 "\t" $5
    }' | sort -f
} | column -t -s "$(printf '\t')"

Headers distinguish package, version, architecture and short description. Only packages with installed status are selected; the search targets package names, not descriptions. column aligns tabs without truncating versions or names. Results can therefore differ from the original grep over whole lines.

If column is unavailable, remove | column … to obtain TSV; Ubuntu provides column in bsdextrautils. On a narrow terminal, use the card report below to avoid a very wide table.

UBUNTU HOST TO INSPECT · Bash
dpkg-query -W -f='${db:Status-Status}\t${binary:Package}\t${Version}\t${Architecture}\t${binary:Summary}\n' |
  awk -F '\t' '$1 == "installed" && $2 ~ /(libgtk|libqt|xserver)/ {
    printf "\nPACKAGE     %s\nVERSION     %s\nARCH        %s\nDESCRIPTION %s\n", $2, $3, $4, $5
  }'

Interpreting your output: the supplied rows show installed GTK/Qt components and x11-xserver-utils. They do not by themselves identify launchable GUIs. Use the launcher search to obtain paths for Tilix, Stacer or TigerVNC; use the Depends-field search to connect packages with libraries.

Structured inventory of desktop candidates

The following command produces tab-separated rows (TSV): it reads only the main Desktop Entry group and excludes entries with a Type other than Application, Hidden=true or Terminal=true. It never executes Exec or TryExec.

UBUNTU HOST TO INSPECT · Bash
printf 'Name\tExec\tTerminal\tTryExec\tDesktopFile\n'
for dir in /usr/share/applications /usr/local/share/applications \
  "${XDG_DATA_HOME:-$HOME/.local/share}/applications" \
  /var/lib/snapd/desktop/applications \
  /var/lib/flatpak/exports/share/applications \
  "$HOME/.local/share/flatpak/exports/share/applications"; do
  [ -d "$dir" ] || continue
  find -L "$dir" -type f -name '*.desktop' -exec awk '
    /^\[Desktop Entry\]\r?$/ { main=1; next }
    /^\[/ { main=0 }
    main && /^[A-Za-z]+=/ {
      key=$0; sub(/=.*/, "", key)
      value=$0; sub(/^[^=]*=/, "", value); sub(/\r$/, "", value)
      gsub(/\t/, " ", value); field[key]=value
    }
    END {
      if (field["Type"] == "Application" && field["Hidden"] != "true" &&
          field["Terminal"] != "true") {
        printf "%s\t%s\t%s\t%s\t%s\n", field["Name"], field["Exec"],
          field["Terminal"], field["TryExec"], FILENAME
      }
    }' {} \;
done

It keeps NoDisplay entries and launchers without Exec so that D-Bus-activated candidates are not lost. Name is the base name, not the desktop translation. The filter does not prove that a window exists or that the program is correctly installed.

Limitations: this is a per-file inventory, not a reconstruction of the menu. It may contain duplicate or stale launchers; it does not resolve user/system override precedence, OnlyShowIn/NotShowIn or all custom XDG_DATA_DIRS locations. Excluding Terminal=true can omit programs with mixed modes.

Installed packages with graphics dependencies

UBUNTU HOST TO INSPECT · Bash
dpkg-query -W -f='${db:Status-Status}\t${binary:Package}\t${Version}\t${Depends}\n' |
  awk -F '\t' '$1 == "installed" &&
    $4 ~ /(^|[ ,|])(libx11-6|libxcb1|libgtk-3-0|libgtk2.0-0|libgtk-4-1|libqt5gui5|libqt5widgets5|libqt6gui6|libqt6widgets6)([ :,(|]|$)/ {
      print $2 "\t" $3 "\t" $4

This searches the Depends field of actually installed packages, rather than just package names. Libraries or components without a user interface may appear: inspect the candidates. The filter is partial (declared direct dependencies); it can miss transitive dependencies, plugins and other toolkits. It does not cover the contents of Snap, Flatpak or AppImage.

dpkg-query(1) · Ubuntu Jammy

Why the three suggested commands cannot provide certainty
  • grep -r "Name=" … may include GenericName and action names, while missing launchers in other locations. A .desktop entry can launch a service or a text program.
  • ldd … | grep libX11 shows a library dependency: it proves neither the selected backend nor remote operation. GTK and Qt support multiple backends and are not simply “Xorg libraries”.
  • dpkg -l | grep -E "libgtk|libqt|xserver" filters rows by text: it mainly finds libraries/servers, not all applications using them, and can include states other than installed. A remote X server is not a forwarding requirement.

Conclusion: find the candidate → check the command/package → observe X11 → test the GUI over SSH. None of these filters is a “mathematical certainty”.

Deeper inspection: all launcher metadata

Run as the user you are investigating. This searches common launcher locations, including Snap and Flatpak exports, and skips missing directories.

UBUNTU HOST TO INSPECT · Bash
for dir in /usr/share/applications /usr/local/share/applications \
  "$HOME/.local/share/applications" /var/lib/snapd/desktop/applications \
  /var/lib/flatpak/exports/share/applications \
  "$HOME/.local/share/flatpak/exports/share/applications"; do
  [ -d "$dir" ] || continue
  grep -RHnE '^(Name|Exec|TryExec|Terminal|Type|Hidden|NoDisplay)=' \
    "$dir" --include='*.desktop'
done

Exec= identifies the launch command; Terminal=false means no terminal is requested, not that the app uses X11. Fields such as %U and %F are launcher placeholders: do not blindly paste them into Bash. Secondary actions, duplicates and hidden launchers may appear; custom XDG paths and software without launchers can be missed.

References: Desktop Entry Specification · freedesktop.org

Complete the inventory: APT, Snap and Flatpak

UBUNTU HOST TO INSPECT · Bash
dpkg-query -W -f='${binary:Package}\t${db:Status-Status}\t${Version}\n' | \
  awk -F '\t' '$2 == "installed" {print $1 "\t" $3}'
if command -v snap >/dev/null 2>&1; then snap list; fi
if command -v flatpak >/dev/null 2>&1; then flatpak list --app; fi

The list also includes software without a GUI. An APT package inventory does not automatically cover Snap, Flatpak, AppImage, programs in /opt or manual installations. For each candidate, record its name, version, source and command. Do not bulk-launch the Exec entries you find.

Deeper inspection: look for library clues

Optional: install binutils and file for these commands. This example uses xclock; replace it with the executable you found.

UBUNTU HOST TO INSPECT · Bash
app_path=$(command -v xclock)
if [ -n "$app_path" ]; then
  file -L "$app_path"
  readelf -d "$app_path" | grep NEEDED
fi

libX11, libxcb, GTK or Qt are clues, not a verdict. readelf shows direct ELF dependencies, not all transitive or plugin-loaded ones. Scripts, wrappers and static binaries need different analysis; a “not an ELF file” error does not rule out a GUI. Avoid ldd on untrusted executables.

References: readelf(1) · Ubuntu Jammy

Use ldd only on a trusted executable

After checking with file that the path is a trusted dynamic ELF executable, you can also inspect dependencies resolved by ldd. This example uses xclock; do not use a wrapper or an unknown file.

UBUNTU HOST TO INSPECT · Bash
app_path=$(command -v xclock)
if [ -n "$app_path" ]; then
  ldd "$app_path" | grep -Ei 'libX11|libxcb'
fi

A match indicates linked libraries, including indirect dependencies; no match does not rule out runtime-loaded plugins. It proves neither the need for nor compatibility with forwarding. Prefer static inspection with readelf for untrusted executables: ldd can cause code execution.

References: ldd(1) · Ubuntu Jammy

04

Observe X11

To inspect applications already running, use a terminal inside the desktop you are investigating, as its user. An SSH session with forwarding may point to the client’s local display, not the remote machine’s physical desktop.

TERMINAL ON THE DESKTOP TO INSPECT · Bash
printf 'DISPLAY=%s\n' "$DISPLAY"
xlsclients -l
xprop WM_CLASS WM_NAME _NET_WM_PID WM_CLIENT_MACHINE

With xprop the pointer changes: click the window you want to identify. WM_CLASS helps identify the app; _NET_WM_PID, when present and correct, identifies a process on the computer named by WM_CLIENT_MACHINE. Do not use that PID on the wrong computer.

Important limitation. xlsclients is not a complete census: it depends on properties published by clients. It does not show native Wayland windows and may omit X11 clients. On Wayland, a window recognized by xprop uses X11 through Xwayland. Absence from the list does not prove an app is Wayland.

References: xlsclients(1) · Ubuntu Jammy · xprop(1) · Ubuntu Jammy · Xwayland · Wayland documentation

From a PID to the process and its environment

On the computer running the process, replace 1234 with the verified PID. Inspect your own processes: permissions, containers and namespaces may limit visibility.

UBUNTU HOST TO INSPECT · Bash
target_pid=1234
ps -p "$target_pid" -o pid=,user=,comm=,args=
readlink -f "/proc/$target_pid/exe"
tr '\0' '\n' < "/proc/$target_pid/environ" | \
  grep -E '^(DISPLAY|WAYLAND_DISPLAY|GDK_BACKEND|QT_QPA_PLATFORM)='

DISPLAY or WAYLAND_DISPLAY in the environment are only inherited clues: they prove neither a connection nor the backend actually used. The PID may have exited, been reused or not been published by the window.

05

Verify over SSH

1. Check the remote service

UBUNTU HOST TO INSPECT · Bash
command -v xauth
sudo /usr/sbin/sshd -T | grep -E '^(x11forwarding|x11uselocalhost|disableforwarding|xauthlocation) '

Check for x11forwarding yes, x11uselocalhost yes and disableforwarding no. With Match rules, also use sshd -T -C with the actual user and addresses: the global configuration may not match your connection. SSH key restrictions may prohibit forwarding.

If the configuration needs adjustment

The administrator should inspect /etc/ssh/sshd_config, included files and Match rules. Set X11Forwarding yes while keeping X11UseLocalhost yes where appropriate; do not blindly append duplicate directives. After editing, validate and reload the service:

UBUNTU HOST TO INSPECT · Bash
sudo /usr/sbin/sshd -t && sudo systemctl reload ssh

Keep the current session open and test a new connection. Reloading does not add forwarding to an existing session.

References: sshd_config(5) · Ubuntu Jammy

2. Open the tunnel from your local computer

From a local Ubuntu terminal with an X server available. Replace user@host with your destination. First check that DISPLAY is set on the client.

SSH CLIENT · LOCAL COMPUTER · Bash
printf 'DISPLAY=%s\n' "$DISPLAY"
ssh -X -o ForwardX11Trusted=no user@host

This explicitly requests untrusted forwarding. On Ubuntu/Debian, -X alone may already be trusted; do not infer the trust level from the letter alone. An application incompatible with the restrictions may need ssh -Y, for trusted hosts and applications only: it grants broad access to the local display.

3. Test a simple window

NEW SSH SESSION · REMOTE HOST · Bash
printf 'DISPLAY=%s\n' "$DISPLAY"
xclock

A value such as localhost:10.0 is typical, not mandatory. If the clock appears on your screen, the X11 path works for that client. Close it to return to the prompt. Do not manually set DISPLAY to :0 or your computer’s IP: that would bypass the display prepared by SSH.

References: ssh(1) · Ubuntu Jammy

4. Test the candidate application

In the same session, launch one trusted application using the command identified earlier. To avoid reusing an existing process, first close its instances after saving your work, or use the program’s documented new-instance option.

SSH SESSION · EXAMPLES TO ADAPT · Bash
GDK_BACKEND=x11 gtk_app_name
QT_QPA_PLATFORM=xcb qt_app_name

The two lines are alternatives for GTK 3 and Qt 5: substitute a real command and run only the relevant one. They work when the build includes the backend and its dependencies. They do not globally change the desktop. D-Bus, sandboxes, graphics acceleration or existing instances can complicate launching.

References: GTK 3 · Running applications · Qt 5 · QGuiApplication

06

Troubleshoot

Empty DISPLAY or “Can’t open display”
First check the local X server and DISPLAY, then reconnect with forwarding. Check xauth and the effective sshd configuration. For details use ssh -vv -X -o ForwardX11Trusted=no user@host. Logs may contain names and addresses: redact them before sharing.
“Authorization required” or rejected X11 cookie
Try as the SSH session user, without sudo when launching the GUI. Check ownership and permissions of the authorization file (XAUTHORITY, if set), then reconnect. Do not publish xauth cookies or use xhost + as a shortcut.
The desktop uses Wayland and xlsclients shows little
This is expected for native Wayland apps. xlsclients observes the selected X display, not the Wayland compositor. Try xprop on the window and check the application’s documented backend.
“Could not load the Qt platform plugin xcb”
Check the plugin dependencies and the Qt environment of that installation. This message alone does not prove a tunnel failure. Confirm xclock first and avoid mixing Qt libraries from different installations.
It works initially, then new launches fail
In untrusted mode, ForwardX11Timeout limits how long new X11 connections are accepted (upstream default: 20 minutes). Open a fresh session and inspect the client configuration. Also check for SSH disconnects and computer sleep.
Snap, Flatpak, browsers or a slow GUI
Check graphics permissions and limitations of the specific package, as well as D-Bus and acceleration. Do not disable the sandbox as a generic fix. X11 forwarding does not guarantee remote GPU support, audio or good performance over high-latency links; remote desktop software may fit better.

For client options: ssh_config(5) · Ubuntu Jammy
